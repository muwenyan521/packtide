# 发布检查清单

本文说明如何准备发布；不表示发布已经完成。首个公开软件包版本目标为 `0.1.1`。本地成功构建不等于可下载的 Release、可复现构建声明或完整的发行版支持声明。

1. 选择源代码提交，审查精确 diff 和[源代码声明](../NOTICE.md)，并保持工作区版本、标签、打包配方和工件名称一致。
2. 按 [CONTRIBUTING.md](../CONTRIBUTING.md) 运行工作区检查。验证实际 CLI 帮助界面、真实 TUI 预览/取消、man 页面、补全文件和运行时依赖。
3. 运行适用的、锁定且一次性的包管理器测试通道并完成清理。将提交、工具链、精确调用、JSON 结果和清理输出一起留存。不可用通道或仓库/网络失败不得标记为通过，并在发布说明中记录剩余限制。
4. 使用发布工作流的基线环境构建 GNU/Linux 归档。包含两个二进制文件、man 页面、补全文件、`LICENSE`、`NOTICE.md`、溯源信息和 SHA-256 校验和。使用临时前缀从解包归档测试安装，并验证卸载范围。
5. 只有审查这些工件后，才能创建/推送匹配的版本标签以触发已配置的发布工作流。发布需要维护者明确授权。
6. 下载上传的归档和校验和并验证，保留其哈希和源代码提交。只公布确实能够下载和验证的工件。

`commands/release-sha256.txt` 保存早期本地构建的校验和记录，不是新发布的校验和清单。必须从最终工件生成全新的校验和。发布 profile 使用 thin LTO、8 个 codegen 单元、剥离符号和 panic 即终止；这些设置本身不能证明逐位可复现。

## 发布说明

描述行为净变化、支持的能力/作用域路径、运行时要求、已验证场景和已知限制。初始版本要区分多发行版原生后端与 Arch 专属的镜像/降级功能；在支持的发行版上，`packtide sysup` 转发到唯一的 `systide` 编排实现。缺少可选工具时会跳过；原生后端失败会停止更新序列；已尝试的可选后端失败只发出警告，后续可选提供方仍会尝试。原生更新成功后，可选失败不会改变退出状态 0；发布说明不得将此描述为每个提供方都成功。
